# Releasing

Cut a release when `git log $(git describe --tags --abbrev=0 origin/main)..origin/main` contains a behaviour change: models, login, provider, install, runtime or `peerDependencies` changes, security fixes. Docs-, CI-, test- and devDependency-only commits wait for the next one. The agent that merged the change releases; a change merged by the owner (outside PRs, security advisories) is released by the next agent working in the repository. One release covers every change since the previous tag. `package.json` `version` and the README pinned-install example match the tag; `main` stays the default install.

1. Pick the version (the project is `0.x`; `1.0.0` is the owner's decision): patch for fixes and additions that keep existing setups working, such as a new model; minor for new commands or capabilities and anything that removes or renames a model or provider ID, changes the login flow or raises the `peerDependencies` floor.
2. Land a `chore(release): v0.x.y` PR through the landing steps in [AGENTS.md](../AGENTS.md) that changes only the version: `npm version --no-git-tag-version 0.x.y` (updates `package.json` and both `package-lock.json` fields) and the README pinned-install example.
3. Right after the release PR merges, on its merge commit: `gh release create v0.x.y --target <full sha from gh pr view <n> --json mergeCommit -q .mergeCommit.oid> --title v0.x.y --notes-file <file>`. Until then the README points at a missing tag, so do this before anything else lands. Notes list the user-visible changes since the previous tag (`git log <previous tag>..<merge sha>`) with PR numbers and credit outside contributors. Report the release URL.
